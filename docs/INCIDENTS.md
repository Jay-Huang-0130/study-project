# 生成阻塞維護紀錄

## 2026-10-27：送出 turn/start 後未收到啟動確認

**觀察**：正常時間線有 thread、RPC ACK、turn/started、回答、完成。故障時間線停在「App 已送生成指令」，沒有 ACK 或後續活動；使用者暫停重啟有時恢復。0.10.3 補強後，使用者回報這次完整跑完未遇到問題。

**確認的程式缺口**：舊 send 使用 `this.child?.stdin.write(...)`，child 不存在時靜默略過；未確認 stdin 可寫狀態、非同步 callback 或 backpressure。因此舊「已送出」不構成真正寫入成功的證據。這些缺口已確認，但沒有當次完整管道紀錄，不能斷言所有歷史阻塞都由同一原因或排除所有上游因素。

**已修補、不得回退**：rpc-writer 的 FIFO、存活及可寫檢查、callback 成功／失敗、drain 背壓、30 秒本機寫入期限、取消與關閉清理、舊 child 身分保護、精確 turnId 中斷與遲到結果保護。原有 8 分鐘模型等待政策不因移除間隔而更改。管道不會自動重送，避免重複推論。

**判讀順序**：準備送出 → 寫入開始 → callback 完成（只代表本機管道）→ RPC ACK 或 turn/started → 模型活動 → 回答 → 完成 → 解析／保存。ACK 和 started 可能亂序；只有缺 ACK 不能定為故障。卡住時看當次 pending writeState、管道事件、child 狀態及該請求事件；累計收到訊息數不是當次請求成功證據。

**回歸要求**：保留 rpc-writer、codex 協定及脫敏診斷測試；缺 child、管道關閉、非同步失敗、背壓及取消皆須明確處理。不得以改成固定睡眠、盲目重送或提高併發取代傳送正確性。

**0.11.0 決策**：依使用者成功回報，移除固定 5 秒節流；這只拿掉人工等待，不宣稱真實服務無排隊／速率限制。保留單一請求、多頁批次與完整錯誤觀測，另加入按教材完成後接續的 FIFO。效能比較見 [PERFORMANCE](PERFORMANCE.md)。
